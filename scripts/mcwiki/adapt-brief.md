# 生电 Wiki 条目改写规范（子代理必读，全文照做）

你要把 Minecraft Wiki（中文，CC BY-NC-SA 3.0）的源页面素材，改写成**玄剑公会 Wiki 自己的条目**。
一个字总结你的任务：**改写**，不是复制、不是摘要堆叠、不是翻译。

## 0. 铁律（违反即失败）

1. **不得逐句照抄**。任何与素材原文连续重合 ≥ 20 个汉字的句子都不允许出现。
   正确做法：读完素材 → 合上素材 → 用自己的话把同样的知识点讲一遍（换语序、换句式、合并/拆分句子）。
2. **数值与专有名词可以原样保留**（事实不受版权保护）：方块名、英文名、ID（如 `minecraft:comparator`）、
   信号强度、刻数、高度、Y 值、概率、掉落数量、配方材料、维度名等，必须与素材一致，**不许自己算也不许估**。
3. **素材里没有的不要写**。不确定的数值、机制、版本行为，宁可不写，也不要编。
4. 简体中文，客观说明文体。不要出现「本文」「我们」「笔者」「综上所述」，不要 emoji，不要感叹号。
5. 素材里的模板残留（如 `minecraft:comparator红石比较器`、`[仅Java版]` 之外的孤立代码、重复的方块名）
   属于噪声，**直接忽略**，不要写进正文。

## 1. 输入与输出

输入：`data/mcwiki/prepared/<key>.json`（一张素材卡）

```json
{
  "key": "红石比较器", "title": "红石比较器", "group": "红石基础与元件",
  "sourceUrl": "https://zh.minecraft.wiki/w/...", "revid": 1494508, "license": "CC BY-NC-SA 3.0",
  "lead": "首段纯文本（可能含噪声）",
  "leadTables": [[["材料","配方"],["红石火把","…"]]],
  "outline": ["自然生成","合成","用途", "…"],
  "sections": [{ "title": "用途", "text": "该小节纯文本", "tables": [[["列1","列2"],["…","…"]]] }]
}
```

输出：`data/mcwiki/adapted/<key>.json`（**目录不存在就创建**；文件名与输入的 key 完全一致）

```json
{
  "key": "红石比较器",
  "title": "红石比较器",
  "summary": "≤120 字的摘要，自己话，一句话说清它是什么、干什么用",
  "group": "红石基础与元件",
  "content": "<h2>概述</h2><p>…</p>…"
}
```

## 2. 正文（content）的结构与写法

固定四段式，**顺序不变**，`<h2>` 用中文标题：

```html
<h2>概述</h2>
<p>……</p>

<h2>关键数据</h2>
<table><thead><tr><th>项目</th><th>数值/说明</th></tr></thead><tbody>…</tbody></table>

<h2>要点</h2>
<ul><li>……</li></ul>

<h2>相关页面</h2>
<ul><li>[[红石火把]]</li></ul>
```

- **概述**：2–4 段，每段 1–3 句。说清「是什么 / 有什么用 / 在生电里怎么用」。
- **关键数据**：**只在素材里确实有表格或明确数值时**才写。可以是参数表（延迟、信号强度、堆叠数）
  或配方表（材料 + 产物）。表格 2–6 列、≤10 行，精简到只保留生电用得上的列，删掉「英文名」「ID」等可省略列也行。
  没有可用数据就整段省略（连同 `<h2>关键数据</h2>`）。
- **要点**：4–10 条 `<li>`。每条一句，讲机制细节、注意事项、常见坑或使用条件（如「仅Java版」「需要含水」）。
- **相关页面**：3–8 条 `<li>[[标题]]</li>`，标题只能取自白名单（见第 3 节）。

长度：正文中文 **300–900 字**（不含表格）。宁可短而准，不要长而空。

## 3. 内链白名单

`[[标题]]` 只允许引用 `data/mcwiki/prepared/_index.json` 里出现过的 title（这些是即将一起导入的页面）。
先读该文件拿到白名单；不在白名单里的概念**不要加链接**（直接写文字即可）。
`相关页面` 里的链接必须来自白名单。除白名单外不要使用任何 `[[...]]`。

## 4. HTML 子集（只允许这些标签）

`h2 h3 p ul ol li strong em code pre blockquote table thead tbody tr th td caption br hr a`

- 不要 `class`、不要 `style`、不要 `svg`、不要 `img`、不要 `div`/`span`、不要内联事件。
- 加粗只用 `<strong>`；代码/ID 用 `<code>`。
- 需要外链时：`<a href="https://..." target="_blank" rel="noopener">文字</a>`（少用，主要靠白名单内链）。
- **不要写来源与许可声明**：发布脚本会自动追加统一的来源页脚，你写了会重复。

## 5. 标题命名

`title` = 素材卡 title 去掉 `Tutorial:` 前缀后的中文名。例如：

- `Tutorial:刷怪塔` → `title: "刷怪塔"`
- `Tutorial:铁傀儡陷阱` → `title: "铁傀儡陷阱"`
- `红石比较器` → `title: "红石比较器"`

`key` 字段必须与输入文件名一致（含 `Tutorial:_` 这类前缀），不要改。

## 6. 自检清单（写完每条都要过一遍）

- [ ] 有没有任何连续 ≥16 汉字与素材原文重合（表格、英文名、配置键、数值不算）？有 → 重写那句。
- [ ] 每个数值都能在素材里找到出处？找不到 → 删。
- [ ] `content` 里有没有出现第 4 节之外的标签？有 → 删掉标签保留文字。
- [ ] `[[...]]` 是否全部来自白名单（用最终标题，不要带 `Tutorial:` 前缀）？
- [ ] `summary` 是否 ≤120 字且不自带「本文」？
- [ ] JSON 是否合法（能用 `JSON.parse` 解析）？中文是否正常（不要出现 `\uXXXX` 乱码）？

## 6.5 机器质检 + 自我修正（必做，别跳过）

在你的工作目录执行：

```bash
node scripts/mcwiki/05-validate.js
```

它会逐页输出 `合格 / 告警(!) / 不合格(✗)`，不合格行里会直接给出**与原文重合的违规原句**与字数。

处理规则：

- **不合格（✗）必须清零**：对你负责的每个 key，按报告里那句原话重写该句（保留全部事实与数值），
  再跑一次脚本，直到**你负责的 key 不再出现在 ✗ 列表**为止。反复迭代是正常的，通常 1–2 轮就干净。
- **告警（!）可以接受**：12–15 字的重合多为数值、配方、专有名词，属于规范允许一致的内容。
  但如果告警里的片段明显是一整句人话，顺手改掉更好。
- 脚本会同时列出别人负责的页面（它们可能在改写中途，显示为 ✗）——**只关心你负责的 key**。

## 7. 输出方式

用 write 工具逐个写入 `data/mcwiki/adapted/<key>.json`。
全部写完后，只回一行汇总：`OK <成功页数>/<总页数>`，若有失败页列出 `key` 与原因。
不要回正文内容。
